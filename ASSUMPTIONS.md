# Assumptions & decisions log

Running log of decisions made while scaffolding this project, split into **settings/switches** (easy to change later, safe to assume) and **locked architecture** (expensive to reverse — flagged for discussion before/while implementing). See `astro-properties-roadmap.md` for the original research this project is based on, and `ROADMAP.md`/`TODO.md` for live task tracking.

## Locked architecture (discussed / confirmed)

| Decision | Chosen | Why |
| --- | --- | --- |
| npm package scope | `@davidsneighbour/astro-properties` | Confirmed by user: package scope always matches the GitHub owner the repo actually lives under (`davidsneighbour`), not the `dnbhq` org that the shared tooling happens to be scoped to. |
| Distribution shape | Single repo, npm workspaces monorepo: `packages/astro-properties` (publishable theme/integration) + `apps/demo` (example site) | User asked for one theme, one example site, all issues/PM in one repo. A monorepo satisfies all three without a second repo — npm workspaces let the demo consume the package via a local `file:`/workspace link while both live under one `.git`. |
| Styling | Tailwind CSS 4 + shadcn/ui, **not** the original research doc's "unstyled + CSS variable tokens" recommendation | User's explicit tech-stack list overrides the doc's §10 open question #1. This is a real trade-off, noted below. |
| shadcn/ui integration | React islands via `@astrojs/react` | shadcn/ui components are React + Radix UI under the hood — there is no framework-agnostic port. Using the official shadcn CLI/components means the theme now has a React runtime dependency for interactive UI, which it wouldn't need in a "framework-less Astro" approach. |
| Astro / Tailwind versions | Astro 7 (stable), Tailwind 4 (stable) | The original doc said "target Astro 6, avoid the Astro 7 alpha" — that was true when written; Astro 7.0 and Tailwind 4 are both stable on npm as of 2026-07-12. Confirmed via `npm view astro version` / `npm view tailwindcss version`. |
| Authoring format | YAML frontmatter + **MDX** body for `properties`/`developments`; **TOML** for `agents`/`agencies`/`offices` and site-wide config | Per user instruction: "toml configurations for everything in data files and yaml configuration for front matter data." Entities with a long-form body (properties, developments) get frontmatter+MDX; pure structured records without a body get TOML. MDX (not plain Markdown, as the original doc specified) is used for property bodies so authors can embed components (e.g. inline `EnergyGraph`) — this is what makes the explicitly-requested `@astrojs/mdx` dependency actually load-bearing rather than unused. |
| Package manager / monorepo tooling | npm workspaces (not pnpm) | Matches every existing `dnbhq`/`davidsneighbour` config package convention observed on GitHub (`workspaces` field in root `package.json`, `npm ci`/`npm publish` in CI, no `pnpm-lock.yaml` anywhere in the org). Consistency with the rest of the tooling ecosystem outweighs pnpm's disk/speed advantages here. |
| Shared tooling | `@dnbhq/{biome,tsconfig,markdownlint,renovate,release}-config` | Explicit user request. Usage patterns pulled directly from each package's GitHub README (`dnbhq/biome-config`, `dnbhq/tsconfig`, etc.), not guessed. |
| Testing | Vitest + `@vitest/coverage-v8` + Astro Container API for component tests; Playwright reserved for later once there's a UI worth driving end-to-end | Not in the user's explicit stack list but the natural default for "test everything, keep coverage high" in an Astro project. Not a locked/hard-to-reverse choice — flagged here mainly so the reasoning is visible. |
| License | MIT (unchanged) | Repo already ships an MIT `LICENSE` file; kept as-is. |

### The real trade-off worth flagging

The original research doc's own lesson (from studying Houzez/EPL/Property Hive/WP-Property) was: **"stay theme-agnostic with minimal CSS so the package adapts to any host site."** Requiring Tailwind 4 + React + shadcn/ui moves this project away from that lesson — a consumer now needs Tailwind and React configured to use the interactive components, not just "install and go." This was an explicit instruction from the user (tech stack list), so it's being treated as decided rather than re-litigated, but it changes the pitch from "drop into any Astro site" to "adopt this design system." Worth keeping in mind when writing the package README's positioning.

## Settings / switches (safe defaults, easily changed later)

These are implementation details chosen to keep moving — all are config values, not architecture, so changing any of them later is a small diff, not a redesign.

* **Default currency**: `USD`. **Default area unit**: `sqm`. Both configurable per-site (global default) with per-listing override, per the original doc's §10 recommendation.
* **Default map provider**: OpenStreetMap raster tiles (free, no API key needed for a public demo). Swappable via `map-providers.ts` per the doc's §4 design.
* **Coverage threshold**: starting at 80% lines/branches for new code, intended to ratchet up over time rather than being loosely enforced from day one.
* **Node engines**: `>=22` for the theme package (Astro 7's own minimum), even though the `@dnbhq/*` tooling packages themselves declare `>=25` as their own dev requirement — consumers of the published theme shouldn't be forced onto a newer Node than Astro itself requires.
* **shadcn style variant**: not yet chosen (New York vs Default) — cosmetic, tracked in `TODO.md`.
* **Deploy target for the demo site**: Cloudflare Pages. Confirmed by the user 2026-07-12 (over Netlify, whose MCP connector isn't authorized). `apps/demo/wrangler.jsonc` + the `deploy` npm script + `.github/workflows/deploy-demo.yml` are wired up; the workflow needs `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID` repo secrets before it can actually deploy — tracked in `TODO.md` (#17).
* **Seed content's "market"**: generic/mixed (no specific country/currency skew) unless told otherwise — tracked in `TODO.md`.
* **TypeScript pinned to 6.0.3, not the newer 7.x line**: npm shows `typescript@7.0.2` as latest, but the surrounding Astro tool ecosystem hasn't caught up yet — `@astrojs/check` (which powers `astro check`) only declares peer support for TypeScript `^5 || ^6` and fails to install (`ERESOLVE`) against TS7. Confirmed by the user: "keep typescript at 6, the new version 7 is not ready for astro yet." Revisit once the Astro toolchain adds TS7 support.
* **Biome does not lint `.astro` files** (`!**/*.astro` in root `biome.json`): Biome 2.5's Astro support only analyzes the frontmatter script block in isolation, so it produces false-positive `noUnusedVariables` errors for every prop only used in the template body below the `---` fence (confirmed directly — `PropertyCard.astro`'s `areaSize`/`areaUnit`/`labels`/`class` are all used in the template, but were flagged as unused). Until Biome's Astro support understands template usage, `.astro` files are excluded from Biome and rely on the Vitest/Container API tests + `astro check` (in `apps/demo`) for correctness instead.
* **`index.ts` was removed; the package has no barrel file**: `@dnbhq/biome-config` turns on `noBarrelFile`/`noReExportAll` as hard errors, and the package's `package.json` `exports` map already exposes every subpath directly (`./schema`, `./content-schema`, `./components/*`, `./layouts/*`, `./lib/*`), so a re-exporting `index.ts` was redundant as well as against the shared lint policy. The `"."` export now points straight at `./src/schema.ts`, the package's core value-add.
* **`packages/astro-properties` typechecks with plain `tsc --noEmit`, not `astro check`**: the package is a component library, not a full Astro site — it has no pages/routes for `astro check` to validate, so plain `tsc` is sufficient and simpler. `apps/demo` uses `astro check` since it consumes the components through real pages, which is where meaningful prop-usage type checking happens anyway. The package's own `.astro` files get a permissive `declare module "*.astro"` ambient shim (`src/astro-modules.d.ts`) so plain `tsc` doesn't choke on the import itself — real behavioral coverage of those components comes from the Vitest + Container API tests, not from `tsc`.
